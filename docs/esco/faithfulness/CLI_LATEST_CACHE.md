# Bounded latest-release notification cache

This control-only correction starts from main `95c85b390db6b5b1b742c1a16ba87ce2d0d5ba3d`. Runtime/source/SQL and every workflow, permission, CLI/action pin, deployment target and baseline remain unchanged. Parent review precedes integration or operational execution.

Official CLI tag v2.122.0 resolves to commit `5afad870388552d0198087d27037da7ac745ba2b`. Its [path definitions](https://github.com/supabase/cli/blob/5afad870388552d0198087d27037da7ac745ba2b/apps/cli-go/internal/utils/misc.go) place `cli-latest` in `supabase/.temp`, outside functions. [GetLatestRelease](https://github.com/supabase/cli/blob/5afad870388552d0198087d27037da7ac745ba2b/apps/cli-go/internal/utils/release.go) returns the latest GitHub release tag verbatim. [checkUpgrade and Execute](https://github.com/supabase/cli/blob/5afad870388552d0198087d27037da7ac745ba2b/apps/cli-go/cmd/root.go) write raw tag bytes without an added newline, refresh after ten hours or with --version, and use the value for a notification after command completion. They can also write an empty value on lookup failure. Upstream imposes no tag grammar or byte cap. The cache does not select or upgrade the pinned executable; the [function downloader](https://github.com/supabase/cli/blob/5afad870388552d0198087d27037da7ac745ba2b/apps/cli-go/internal/functions/download/download.go) does not consume it.

Our stricter policy permits only the exact regular file `supabase/.temp/cli-latest`, 1..128 ASCII bytes: a `vMAJOR.MINOR.PATCH` SemVer tag with optional valid prerelease/build identifiers, no leading zero in numeric core/prerelease identifiers, whitespace, control bytes, empty value or normalization. Build identifiers may have leading zeroes under SemVer. This is an explicit defensive policy, not a claim that upstream enforces it. Missing/unknown layouts fail closed.

The filesystem reader checks both ancestor directories, opens the file without following its final symlink and with nonblocking mode, checks regular-file type/size and stable descriptor size/timestamps, and reads at most129 bytes. It returns validated bytes privately. The exact inventory still compares their length/hash with the independent raw snapshot. Legacy pure callers lacking observed bytes retain the old exact v2.122.0 expectation; hashes alone cannot authorize a different cache. Diagnosis uses the same observed-byte validation and then still invokes full reconstruction. Invalid cache input exposes the existing fixed RAW_LAYOUT_REJECTED code, never contents, raw paths or exception bodies.

Unchanged: exact linked-project.json bytes/hash; all other cache paths; inventory entries/key shapes/order; wrappers; seeded config; native83 equality; only two pinned type-only omissions; TypeScript5.9.3 AST/reference proof; reconstructed85 equality; CLI2.122.0; source/recovery SHA/tree/fingerprints; v288 metadata/config; two fresh captures; exclusive window, ownership/health/source checks and conditional safe rollback. Different valid notification tags across captures do not change source/config requirements. Original raw capture is never rewritten or copied into clean recovery; cache is outside the reconstructed source. Filesystem rereads are not atomic snapshots. Rollback proves source/configuration recovery, not identical binary recovery.
