# Prepared Telegram clinical confirmation callers

Both edge roots now route clinical alert “sí” and pending-step selection in the native treatment conversation through clinicalStepConfirmation.ts. The alert callback reads and pins its original type, then prepares before any legacy claim. Nonclinical/negative alert lifecycle remains separate. The conversation hands off to the prepared private message and does not announce a confirmed step. RPC177 and direct clinical UPDATE are no longer called by these routes; their database permissions remain pending the separate retirement unit.

A private original sender/chat/message anchors every operation. Preparation persists the pending original intent in the session before RPC and never posts. Only a separately delivered preview of the captured animal/treatment/step/programmed/application dates carries the final confirmation. Independent recovery middleware precedes conversation replay; it queries the original native action through fresh server authority. A post from a message without that exact prepared preview only renders the preview and requires another click. Cancellation fences and status survive session/conversation loss; retrying an unacknowledged preparation requires the same saved action/intent. No new action is generated automatically after uncertainty. A sessionless unknown action can be verified or canceled, not re-created with invented intent.

The strict receiver is byte-identical to the browser receiver and both edge mirrors. It validates original actor/action/intent, full source graph and exact immutable receipt changes. Current allowed unlinked Hato workers retain their registration identity; no profile is invented. Linked accounts and registrations are freshly checked by the existing protected RPC. Telegram message editing/broadcast errors after a validated commit do not trigger another post or claim a failed database write. /cancelar checks the clinical fence before clearing the pending session/exiting.
