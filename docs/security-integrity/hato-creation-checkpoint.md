## Identity and roles that must be preserved

Web treatment/standalone pajilla/general ficha creation therefore must not become Gerencia-only by copying the undo rule. A typed prospective `manual_cycle` entry should enforce the existing operation rule; it must not impose that rule on other creation operations. Current effective RLS/ACL must be captured before making policy-equivalence claims.

Telegram `/evento` admission is the existing active registration and `hato_produccion` module, not an Administrador/Gerencia role check. Bot middleware reads an active registration; if linked, it rereads a unique active `usuarios` profile. It expressly preserves active unlinked field workers. `resolverUsuarioTelegram` at write time rereads active registration for `ctx.from.id`, but does not reread/lock application profile or module, and `ok:true` can contain `usuarioId:null`. Thus forcing every creator to a linked Gerencia/Admin profile would narrow existing semantics. The transaction must lock/recheck exactly one active sender registration, current module, and a fresh active profile **if linked**; preserve the unlinked lane using registration ID + actual sender as trusted actor identity, nullable application ID, and canonical display attribution. Any later binding/profile/module change must refuse a replay under a different actor identity, not move the old request to the newly linked account. Creation is private-chat-only under current bot middleware. The linked-only treatment-step confirmation lane remains distinguishable.

Gerencia-only undo stays separate and unchanged. No creator-only undo, age window, new creator role, FIFO batch rule, automatic historical ownership repair or universal linked-worker requirement is proposed. Subscription migration 152 controls alert delivery, not `/evento` creation authorization; its Fernando matching must not be repurposed as a new creation gate.

### Preserve clinical-first degradation deliberately

Current business rule is that failure to create calf or decrement pajilla does not erase the clinical fact. Do not silently change that to mandatory-all-dependents success. One outer SQL transaction can preserve it with narrow savepoint/subtransaction handling for specifically classified expected dependent failures, producing an atomic clinical-only receipt with an explicit immutable reason/outcome. The receipt distinguishes dependency not requested, created with exact new ID, requested but unavailable, and pre-existing inventory use not owned by this command. Requested treatment follow-up is not optional degradation and must roll back with its header on any failure.

A successful event commit never requires a later compensating DELETE over HTTP. All newly created related rows commit with the canonical receipt/provenance, or the entire unexpected/invariant/audit failure rolls back. Catching every SQL exception and returning clinical-only is unsafe: trigger suppression, unexpected side effects, permission/identity drift, malformed dependency state and audit failures must abort. The exact recoverable error allowlist needs a reviewable candidate/test before implementation. Any optional calf/use writes attempted within a failed savepoint are rolled back before the clinical-only result commits; no orphan is visible. Replaying a clinical-only receipt never creates a second event or silently retries/promotes its missing dependent. An explicit later management repair needs its own key and transaction; it cannot fabricate original provenance.

Insemination payload binds the already-selected lote UUID and toro UUID. SQL checks fresh lote.toro_id and actual animal/date; it must not derive a different lote from an unordered toro→lote map. Current Telegram Map overwrites lots sharing a toro without an ordering rule; do not introduce FIFO or highest-stock selection. Keep the exact selected identity and present/reconfirm material change. Zero/negative derived stock continues to warn, never block. Duplicate existing lote/animal/date use is not a newly owned use: do not claim/delete/associate it using timestamps or mutable JSON. A receipt must explicitly record that the command did not create that row.
