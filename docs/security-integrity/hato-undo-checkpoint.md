## Observed callbacks and failure modes

`src/supabase/functions/server/telegram/bot.ts` registers `hato_ev_undo:` around line 1361 and `hato_tr_undo:` around line 1547; deployed source is mirrored under `supabase/functions/make-server-1ccce916/`. Keep distinct prefixes and generated callback payloads below Telegram's 64-byte limit. Current generated callbacks contain only the target UUID; the event parser also accepts older event/usage UUID payloads.

Both callbacks reread unique active Telegram registration and its unique active `usuarios` profile, requiring role Gerencia, before reads and again before deletion. This correctly rejects missing/ambiguous links and revoked profiles, but separate HTTP reads do not hold authorization locks through mutation. The sender comes from `ctx.from.id`. Current code has neither creator-only ownership nor elapsed-time guard; those are observations, not newly required business rules.

Event undo reads source, animal/date/type, mutable `datos`, creation time and calf ID, and requires `fuente = 'telegram'`. It does not currently select/check `chequeo_vaca_id`. Retained calf undo requires the existing automatic-birth marker, same mother, exact unnamed sentinel, active state and no references. Failed/missing reference counts refuse. References checked are events as animal or calf (excluding this event), animals as mother or father, `hato_chequeo_vacas`, `hato_pesajes_leche`, treatments, pajilla uses, alerts and `fin_transacciones_ganado` with `es_hato = true`. A non-intact/referenced calf refuses the entire operation. Missing calf currently means no calf deletion.

Usage selection trusts legacy callback usage UUID first, then `datos.pajilla_uso_id`, then chooses the nearest creation timestamp among uses for the same animal/date. There is no maximum interval, tie refusal, immutable event association, or validated batch/toro/creator match. A failed usage lookup becomes an empty candidate list. This can select another clinical record's inventory use; a caller-supplied UUID is not provenance.

Deletion order is usage, event, calf in separate HTTP requests. Event failure can leave usage deleted; calf failure leaves the event deleted and calf present. Deletes inspect errors rather than returned rows, so a trigger-suppressed/no-op delete can appear successful. Prechecks race with edits and new references. Telegram message editing after mutation can also fail independently of the database result.

Treatment undo reads header/source plus nested executed dates, requires Telegram source and no step with non-null `fecha_ejecutada`, then deletes the header. The local step FK cascades deletion. Confirmation can occur after the precheck and before header deletion. Linked alerts may block the cascade through their step FK; preserving that refusal is safer than inventing alert cleanup. Initial read errors are not distinguished reliably from absence.

Creation is a separate integrity boundary: `/evento` may create a calf before event insertion, insert a usage after the event, then update `datos.pajilla_uso_id` separately. Failed usage intentionally preserves the clinical event; failed link leaves no reliable association. Treatment creation uses `fn_hato_registrar_tratamiento`. Undo alone cannot certify or repair these creation paths.

## Proposed transaction and invariant contract

Expose a narrowly granted service-role RPC for the trusted bot. Ordinary authenticated callers must not be able to impersonate a Telegram sender argument. Resolve the actual update sender inside the transaction to exactly one active binding and active Gerencia profile; hold locks through completion. Align identity lock order with binding candidate: registration first, linked profile second. Reauthorize receipt replay; never infer actor from callback UUID, cached display name or event creator.

Bind a stable request key to actor, sender, operation, target and exact expected payload/proof. Serialize same-key attempts; different payload for the same key refuses. A successful receipt contains canonical target/dependent before and after snapshots, actor/origin, exact deleted IDs and audit evidence. Protect target-level completion against a second fresh request key. Lost replies replay the same receipt; a failed Telegram edit must not cause another domain mutation. If explicit pending resolution is added, use a durable cancellation fence under the same key lock, not an unlocked status read or fresh-key automatic resubmission.

For prospective coupled events, creation must persist a protected association recording exact event, usage and calf IDs and snapshots. Mutable JSON/timestamp matching cannot become historical proof by backfill. Legacy usage UUIDs and nearest-time matches are hints only: refuse any coupled undo whose actual association cannot be proven, without deleting anything. A simple legacy event without coupled records needs a separately bounded reviewed eligibility check; do not silently classify an insemination with absent metadata as proven to have no usage. Preserve the existing intact-calf conditions, and refuse edited/missing/inconsistent prospective dependents rather than manufacture provenance. No new TTL or creator restriction is proposed.

Lock target and all proven dependents in a deterministic order before validation. For calf deletion, hold a lock that conflicts with new FK references, enumerate all actual inbound references, permit only this target's own reference, and recheck actual links after locking. Catalog-discovered cascade or SET NULL relationships must not silently destroy or detach clinical/financial history. If a dependency lacks a real FK, ordinary row locks alone do not fence its insertion; coordinate that writer or refuse deletion until a suitable database constraint/protocol is established. This is an implementation prerequisite, not something a pre-count solves.

For event undo, check fresh canonical fields, Telegram source and absence of chequeo ownership; validate protected usage/calf association. Delete the proven usage, then event, then eligible calf within one transaction. Require exact returned rows, verify final absence and derived batch stock change, and verify audit receipts. Trigger-suppressed writes, unexpected cascades, stale snapshots or any mismatch roll back every effect. All unrelated records and finance/storage remain untouched.

For treatment undo, lock header first, then its complete ordered step set, consistent with 177. Refuse any executed step, non-Telegram source, stale proof or blocking actual references. Locking the header must fence new step insertion through its FK; the metadata check must confirm this. Preserve alerts/deliveries. Cascade only the exact validated step set, confirm returned header and actual deleted steps, and record full before/after audit atomically. Review all other confirmation/update writers: locking only the header is insufficient if a writer changes a step without participating in the compatible lock protocol. Never fall back to client DELETEs or destructive dependency cleanup.

Audit/protocol retention, protected receipt creation, all relevant writer participation and deployment ordering are separate gates. An undo candidate cannot claim global Hato integrity, fix the old general alert callback, or certify the non-atomic event creation flow by itself.

## October 12 bounded implementation and bot handoff

Local files: `src/sql/security-candidates/hato-undo.sql`, `scripts/security/hato-undo-postgres.py`, `src/utils/hato/hatoUndoProtocol.ts`, and `src/__tests__/hatoUndoProtocol.test.ts`. The SQL deliberately implements **standalone undo only**. Event eligibility requires Telegram source, an allowlisted lifecycle type, no chequeo/calf/alert/finance link, no retained-calf marker, and no usage ID in `datos`; service events require explicit `monta`. Insemination, unknown service type, retained calf, any usage hint, and other coupled/ambiguous records refuse entirely. It never trusts a legacy callback usage UUID, mutable JSON association, or proximity of timestamps. It never deletes usages/calves or adjusts pajilla balances. Prospective coupled creation and protected association are still a separate gap. Treatment eligibility requires active Telegram source, no chequeo link, and every step's executed date exactly null. Incoming FK references other than the intentionally cascaded header-to-step relationship refuse, including SET NULL/CASCADE dependencies; alerts and send history remain intact.

Each service-only RPC locks the unique active sender registration before the active Gerencia profile; no Auth GUC impersonation is used. A unique, valid, immediate, nonpartial single-key Telegram sender index is an installation prerequisite. EXCLUSIVE table locks cover roots and recursively catalog-discovered inbound FK relations; treatment header precedes steps. These are deliberately coarse and may impose substantial contention. The candidate captures the complete locked FK footprint before and after and refuses any unexpected change in that footprint. This verifies more than affected row counts, but cannot certify arbitrary trigger side effects outside that footprint, missing non-FK associations, deferred trigger effects, partition DDL changes, or current production writer/metadata parity. Transient full-footprint scan cost/lock contention, affected-record audit retention, and owner/ACL installation review are release gates.

Private RLS-enabled `hato_undo.requests` and `hato_undo.audit` are denied to anon, authenticated, and service_role directly. Success atomically stores the exact request and a target-unique audit with exact affected target/step before/after snapshots, SHA256 attestations of the transient full-footprint invariant states, and the canonical receipt. Returned deleted rows, persisted request/audit, final domain state, and current authorization are checked. Same actor/key serializes via a transaction advisory lock, requires exact payload equality, and replays only with current authorization and matching audit. A fresh key cannot repeat a successful target undo. Explicit resolution uses that same key lock and durably inserts a cancellation fence if no request exists; it is not an unlocked status lookup. A late original post under a cancelled key refuses.

### Root-owned bot integration contract

- `prepareHatoUndo(serviceClient, ctx.from.id, 'event' | 'treatment', targetUuid)` invokes `fn_hato_undo_prepare(p_sender,p_operation,p_target_id)` and returns `{version:1,key,payload}`. Payload is `{actor,sender,operation,target_id,snapshot:{target,steps}}`; target/steps are complete server-canonical row snapshots. An old-message target may have been edited: show the fresh canonical proof for human review before authorizing this attempt; the callback is never original creation proof. Retain this attempt durably under the actual sender before posting, including callback operation/target routing identity. Do not derive actor from callback or creator metadata.
- `postHatoUndo(serviceClient, sender, attempt)` invokes `fn_hato_undo(p_sender,p_request_key,p_payload)` with the original key/payload. The helper accepts only exact actor/sender/key/operation/target, complete expected `before`, and `after:{target:null,steps:[]}` with no unexpected receipt keys. It returns the validated receipt; it never edits Telegram or deletes records directly.
- After a validated success, persist committed status before editing the message. A failed Telegram edit is a presentation failure: keep/replay the same committed attempt. Unknown network/RPC/malformed response keeps the original attempt. Never automatically reprepare or replace the key and never fall back to direct CRUD or dependency cleanup.
- `resolveHatoUndo(serviceClient,sender,attempt)` invokes `fn_hato_undo_resolve` and validates either `{state:'committed',receipt}` or `{state:'cancelled'}`. Resolution is an explicit cancellation action if still absent and must be presented accordingly. Only a confirmed durable cancellation permits a newly reviewed prepare; cancelled original keys remain fenced. Account/sender change refuses locally; profile/binding changes refuse transactionally, including replay.
- Root retains distinct `hato_ev_undo:` / `hato_tr_undo:` parsers and the 64-byte callback cap. Legacy event/usage UUID callbacks may identify the target only; usage IDs are never deletion provenance. Keep both bot mirrors and eventual Deno helper mirrors byte-identical; this candidate helper is currently unwired. SDK tests here exercise the pure helper's actual Supabase HTTP serialization, not real Telegram routing or durable bot attempt storage. Root-owned integration tests must verify those remaining behaviors and no direct-delete fallback.

## Durable Telegram review contract — locally approved and implemented

This contract was saved and sent to root before any shared bot edit. Root approved local implementation, including the read-only status/private review requirements and the cancellation-only recovery correction below. It supersedes the edge-generated-key handoff above for the eventual bot; the committed standalone SQL/helper baseline and its 87/46 checks remain the starting point. Root approval here concerns local flow implementation only; production approval and actual metadata gates remain separate.

**Database owns every attempt.** Add a protected, RLS-enabled attempts table containing actor, actual Telegram sender, server-generated UUID request key, operation, target, exact canonical payload, and terminal state/receipt linkage. Serialize registration by the authorized actor/sender/operation/target under a transaction lock and enforce a unique open attempt for that tuple. A service-only begin/lookup RPC resolves and locks current binding/profile, validates the standalone target, and inserts its immutable canonical payload and key atomically before returning. Repeated original-button clicks, concurrent workers, lost begin responses, and worker restarts recover that same pending attempt; they never generate a replacement key or overwrite its proof. Successful target undo is still target-unique through the private audit. Requests/attempts contain only affected clinical snapshots, never whole-table snapshots.

**An old creation message is only a target selector.** `hato_ev_undo:<targetUuid>` and `hato_tr_undo:<targetUuid>` open a review; legacy usage UUID is never provenance. Enforce the 64-byte cap before parsing (the oversized UUID/usage form refuses). Original callbacks perform no destructive operation. The actor comes exclusively from current `ctx.from.id` and the locked database binding/profile. A group gets only a generic acknowledgement to open private chat; neither target details nor proof/errors are sent to the group. Existing group middleware already stops button use before these handlers; preserve it.

**Send current proof privately, then allow a separate click.** Use `api.sendMessage(actualSender, ...)` to deliver a plain-text Spanish review showing animal number/name, operation, clinical dates/fields, every note/`datos` detail and ordered steps. Internal row/actor UUIDs, source plumbing, and capture timestamps are omitted only from the human presentation; the complete canonical proof remains immutable server-side and all target/step fields participate in CAS. Unknown clinical fields receive plain labels, and an unresolved UUID-only clinical reference refuses confirmation rather than hiding identity. Total preview is bounded to 12 KiB UTF-8 and nested details to 12 levels; refusal yields cancellation-only controls. Render complete preview in chunks of at most 3,500 UTF-16 units without splitting surrogate pairs; no parse mode or silent truncation is used. Only after every review chunk and its final control message succeed, register their exact private chat/message IDs through a service-only delivery RPC under the original attempt lock. A failed/unknown send or failed delivery registration leaves the durable attempt pending and performs no deletion. A preview that exceeds the bound or cannot safely label a clinical reference sends a complete plain refusal explanation and cancellation/status controls only. Those controls are registered with `complete_review=false`; `:c` requires `complete_review=true` at the database even if someone forges the action suffix. `:x`/`:s` remain available for cancellation-only deliveries, and `:n` still requires a confirmed cancellation. Conflicting registration cannot upgrade an incomplete control message. A lost successful send may result in another identical review delivery for the same attempt; this is safe, and each complete delivery is stored as its own exact allowed confirmation message. No expiration or creator policy is introduced.

**Small owner-bound action callbacks.** Final DM controls use the same two prefixes with `<attemptUuid>:c` (confirm), `:x` (cancel), and optionally `:s` (read status), each below 64 bytes. Parsing distinguishes target-only legacy/open callbacks from attempt-key actions. The key is a selector, never authority: every action reauthorizes current sender/binding/Gerencia, requires the stored actor/sender/operation, and requires a private callback chat whose ID equals that sender and whose message ID is a registered complete review delivery. Forwarded review buttons, another sender, group callbacks, wrong operation, unknown key, or unregistered message refuse. Confirmation loads the original immutable payload from the private table; no proof supplied by an edge callback is accepted as replacement evidence.

**Confirm and recover atomically.** The confirmation RPC holds the attempt/request lock, verifies delivery, and performs the existing exact standalone undo transaction against the original canonical payload. A stale target or new reference refuses without rebasing; keep that original attempt until explicit cancellation. A committed duplicate click or a retry after failed Telegram editing returns the same validated receipt with no further domain mutation. Persist terminal outcome/receipt before returning; presentation changes happen afterward and may be retried independently. Status lookup is read-only and must never create a cancellation fence as a side effect. Network/RPC/malformed response preserves the original attempt and renders a private “verify status / retry this attempt” path, never a fresh prepare or a direct DELETE fallback.

**Explicit cancellation is fenced.** The cancel RPC requires the same owner/current authorization/delivered DM identity, acquires the same attempt/request lock, and records the existing durable cancellation fence atomically. It returns committed receipt if confirmation already won, otherwise a terminal cancelled result. Late confirms on that original key refuse. A cancelled attempt is retained. A new attempt requires a separate explicit “Solicitar nueva revisión” action referencing the cancelled original key; the server checks its terminal cancellation and registers a new current canonical proof under the target registration lock. It cannot be produced by automatic retry, an absent status response, or a stale-snapshot error. The new attempt must undergo another successful private delivery and separate human confirmation.

**Public RPC surface and helper testing.** Expose narrowly granted service-only register/lookup/delivery/confirm/status/cancel/new-review RPCs; the existing arbitrary-payload mutation entry becomes a private internal routine or loses public execute grants once durable-review wrappers exist. Preserve all baseline authorization, atomicity, exact receipt, cancellation, minimized-audit, FK-history and 177 concurrency assertions while adapting their setup to registered/delivered attempts. Add real Supabase-transport helper tests and synthetic Telegram adapter tests for both prefixes, callback length/malformed inputs, private delivery before deletion, complete review chunks, sender/message/operation ownership, concurrent begin/lost begin response, restarted worker recovery, stale old-message target, DM unavailable, post/resolve races, and committed receipt recovery after failed message editing. Static guards must verify both bot handlers call only the new review helper and contain no clinical `.from(...).delete()` or association-cleanup fallback. Both bot/helper mirrors stay byte-identical. No other bot handler, production query, export, alert, deployment, or full-suite run is in this slice.
