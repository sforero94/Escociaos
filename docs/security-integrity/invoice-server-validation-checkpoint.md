Existing readers do not consult a validation receipt.

## Concrete server boundary

Propose `POST /make-server-1ccce916/facturas/upload` with multipart fields `{requestKey, protocolVersion:1, tipo:'compra'|'venta', targetKey, file}` and `POST /.../facturas/upload/status` with the exact owner-bound attempt identity/digest fields. Add `POST /.../facturas/upload/target` for versioned owner-target activation/invalidation, and a privileged bounded reconciliation action for quarantined attempts; neither accepts a Storage path supplied by a caller. Target activation returns the canonical server generation for upload/finalize; invalidation returns its durable closed/replaced proof. Owner is always derived from auth.getUser(Bearer), never accepted from form fields. Read exactly one fresh current usuarios profile and require activo===true plus Administrador or Gerencia. Preserve both roles for both tipos: the captured Storage policy allows this, and tipo is a naming hint rather than financial authority. No service JWT, anonymous caller, missing/ambiguous/null-active profile or user-metadata role qualifies as a human upload. Recheck the current profile when reserving/finalizing a request; use database row locks in those short state transitions so an intervening disable/role change cannot silently finalize.

Enforce an outer request limit before buffering, then independently count the actual file bytes with a bounded reader. Content-Length is an optional early refusal, not trusted evidence; multipart overhead needs a documented modest separate ceiling. Reject excess/duplicate file parts, malformed fields, empty content, nonfinite sizes, unknown types, and actual file length >5242880 (exactly 5 MiB allowed). Do not base64-expand files in JSON. Never trust filename, extension, supplied MIME, multipart size or a caller hash as byte proof.

Detect canonical JPEG/PNG/GIF/PDF type from server bytes and validate a bounded structural envelope, including truncation and terminal/container checks. Require the declared allowlisted MIME to agree with detected type; image/jpg aliases JPEG. Require the supplied basename extension to belong to the detected type (jpg/jpeg aliases JPEG; png/gif/pdf exact type), and reject absent/mismatched/unsupported source extensions. Never use that basename as an object path. Generate canonical extension/contentType and object path server-side. A signature-only test is identification, not full validation: select and pin real bounded parsers, or explicitly implement/test their supported container grammar, before claiming structural validation. Fail closed on unsupported/ambiguous container cases rather than silently falling back to File.type. Respect runtime memory/CPU limits and parser resource bounds; compressed images and PDFs can consume much more memory than their input byte length. Do not promise sanitization, malware detection or safe PDF execution from structural checks. PDFs can be structurally valid and contain active content. No paid scanning/OCR/external service is proposed.

After byte validation and reservation, only the trusted edge uses service-role Storage to create the deterministic immutable object with upsert=false, canonical contentType, and no user-chosen bucket/name/owner. The edge does not mutate compras/fin_gastos/fin_ingresos as part of uploading; existing row authorization remains responsible for saving a reference. Upload to `verified/<receiptUUID>.<canonicalExtension>` while its protected record is pending/uploaded and the new authenticated SELECT gate keeps it quarantined. It returns a usable path only after canonical bytes/object identity and a fresh-active/current-target protected committed receipt are verified. No signed URL is minted for an uncommitted object. Do not log file content, signed URLs, access tokens or invoice metadata beyond the minimal diagnostic request identifier.

## Owner, current target, receipt and cross-store retry model

Use protected schema `invoice_upload` with owner/request_key primary identity, protocol version, tipo, stable opaque target_key, canonical MIME/extension, normalized source extension, actual byte length/SHA-256, deterministic path, and explicit pending/uploading/uploaded/committed/quarantined/canceled/unknown state. Persist the reservation before Storage I/O, every known upload outcome, the quarantine reason, and cleanup_pending/cleanup_verified evidence for any abandoned object. A receipt UUID is generated once by the trusted server and bound to the owner/key. The target key identifies the current parent draft/edit session and stable batch row UUID; it is not a caller assertion of financial access. For an existing domain row, keep its ID and current edit/open generation in client context, and keep the domain's own authorization on association. A request must not attach itself to another target or reopen a prior closed dialog. The server must maintain an owner-bound current-target record with a generation/active state, initialized by an authenticated reservation and retired/replaced through authenticated target invalidation. Finalize locks the profile, target and request records and requires the same still-current generation. A client cancellation is server-observed only after invalidation acknowledges; before then the browser generation still prevents stale association, but that alone is not a server fence. Serialize invalidation/finalization so whichever commits first has a truthful outcome, and preserve evidence for a committed-but-no-longer-selected upload rather than attaching it to the new target. Existing domain IDs are checked through their existing authorization when used; a client opaque target token alone never proves a row is writable. New drafts need a durable owner-bound draft UUID rather than assuming a saved database row already exists.

The client reserves `{owner,key,version,target,tipo,size,digest}` before sending and keeps uncertain attempts without a timer that invents failure. Persist no signed URL or File bytes in localStorage. After remount, status uses the exact identity; reupload requires reselecting the same file and checking its actual digest. Browser Web Locks serialize reservation/clear operations. Account, parent target, tipo, open and operation generations gate success callbacks, preview links, file resets, batch row association and durable evidence clearing. Use stable row IDs throughout upload maps; deleting/reordering a row cannot transfer its receipt to the new row at that index. Completing an old request may resolve its receipt but must preserve a newer unsent selection and leave that selection unattached. Owner changes must not restore another owner's batch draft or upload attempt; migrate only the touched invoice-attempt/draft handling deliberately, without claiming a general finance draft redesign.

A committed receipt binds actor, requestKey, protocolVersion, tipo, targetKey/current target generation, path, normalized source extension, actual size, canonical MIME and byte SHA-256. Status binds the same identity and distinguishes committed/quarantined/canceled/unknown; plain `{found:false}` is not proof. Store canonical receipts in service-only protected tables, not a broadly writable public JSON mailbox. Ordinary authenticated/anon users get no direct mutation or finalization RPC; endpoint service helpers accept only already-verified actor IDs and enforce current profile/transition rules. Receipt/status requests are restricted to their human owner even though invoice object SELECT remains available to both existing business roles. Storage object ownership and request ownership are separate.

PostgreSQL state and Storage object writes are not one atomic transaction. An upload accepted by Storage followed by lost finalization/HTTP response must recover the same object/key, not upload another filename. Deterministic names plus upsert=false prohibit overwrite. On conflict/recovery, trusted server verification must establish actual bytes/hash (download/readback as needed); client MIME, object metadata or name alone cannot prove byte identity. After initial Storage success, verify the canonical uploaded object bytes/hash before finalize as well, rather than relying solely on the response path. A validated canonical object can be finalized with the original receipt only if the active profile and current target generation still match under the finalize locks; mismatched/missing uncertain object stays unknown or fails, without automatic delete or association. The receipt represents successful validation/storage, not successful saving of a purchase/expense/income batch.

A status cancel fence can safely mark canceled before any write authorization has been claimed. Once a write is in flight or may have reached Storage, absence cannot establish cancellation: return unknown until the operation is reconciled. Expiring a database lease alone does not stop a delayed Storage request. Design/test fencing and reconciliation before promising canceled/unposted in that state. Do not pretend the CSV transaction cancellation algorithm transfers unchanged across two stores. Durably retain the request/quarantine audit even after narrowly scoped service cleanup of its own uncommitted object. A disabled actor, stale/canceled target, failed final readback or mismatched content never gains a committed receipt: the bytes stay unreadable and the record enters quarantine. Reconciliation may remove only the deterministic new object owned by that quarantined request after proving no committed receipt or surviving financial reference uses it, record the removal result, and recheck absence. A lost/failed remove stays cleanup_pending/unknown with SELECT still denied. Track outstanding upload execution IDs separately from cleanup observations: an absence readback is only absence at that instant, and cannot declare cleanup complete while a delayed authorized Storage request can still arrive. Late arrivals remain hidden because the canceled/quarantined receipt cannot commit; reconcile and remove them using the same retained tombstone. An expired worker lease never promotes a pending file or proves there are no outstanding writes. No TTL should silently grant access or erase evidence, and no existing/referenced invoice, invoice replacement, or previously saved financial association is deleted. Cleanup scheduling/deployment remains separately reviewable; the durable state and bounded explicit reconciliation operation belong to this proposal.

## Direct-upload retirement and Storage semantics

A new server route leaves a bypass if current authenticated Storage INSERT/UPDATE remains available. The proposed review candidate adds restrictive bucket-specific authenticated INSERT and UPDATE policies that deny facturas while leaving every other bucket's behavior intact, plus a restrictive SELECT gate for the new verified namespace. The namespace SELECT helper returns true only for the exact canonical path/bucket recorded in a protected committed receipt; pending/uploaded/quarantined/canceled/unknown or missing records return false. AND this with the original role policies, never replace them with a new permissive owner grant. Thus service-role bytes cannot be signed/downloaded/listed by authenticated readers before finalization, including another Administrador/Gerencia. Legacy names outside the reserved namespace retain their existing policy-equivalent reader access. UPDATE denial must prevent overwrite, upsert and copy/move into facturas, including moves from other buckets via WITH CHECK. The SELECT helper must be SECURITY DEFINER with a pinned search_path and a narrow boolean result, protected-table reads unavailable to ordinary clients, and explicit ACL/ownership checks. Verify the reserved prefix has no legacy name collision before applying the policy (metadata-only names/shape gate); fail installation rather than hide a pre-existing legacy object or relabel it as validated. Capture/verify current policies/grants/roles/API behavior before defining the exact SQL; do not drop guessed policy names or revoke storage.objects privileges globally. Existing SELECT/signing roles and DELETE capability are not silently rewritten in this slice; the new-namespace committed gate is the explicitly requested visibility condition. Test listing, direct download, signed-URL creation and token serving, not merely SQL SELECT. Retaining DELETE is an explicit limitation: authorized users can still remove objects, so receipts cannot promise perpetual file availability. Purchase workflows continue to preserve invoices and perform no deletion. Object-removal retention authority is a separate root decision.

No signed-upload URL or S3 route may remain a human bypass for new invoice bytes after cutover. Review any existing signed-upload tokens and their lifetime/use semantics; do not claim a policy change invalidates pre-issued tokens without hosted evidence. Deploy/verify server capability and coordinate all three browser callers plus SQL denial as one cutover, using a short upload pause or controlled switch if required. This checkpoint does not authorize that release.

Supabase Storage derives owner_id from the upload JWT. A server service-role upload does not establish the authenticated human as Storage owner (commonly owner_id is null/service-created). Verify the hosted behavior; never infer human ownership from a path or fabricate it by inserting/updating storage.objects directly. The captured facturas readers are role/bucket-wide and do not require owner_id, so a service-created object becomes readable under those same policy-equivalent roles only after its new-namespace receipt commits. Trusted actor ownership is kept in the protected upload record. Introducing owner-only Storage readers would narrow existing access and is not proposed.

## Resumed reconciliation contract — 2026-10-12

Before each service Storage upload, claim a fresh execution UUID under profile/target/request locks. Retain execution records indefinitely with the receipt evidence; only a definitive successful or immutable-conflict Storage acknowledgment closes that execution. Transport exceptions, lost responses, and expired processes leave an outstanding execution: no lease/TTL/absence probe can settle it. Readback can still recover and commit immutable matching bytes while the current target/profile matches; quarantine is irreversible and hidden.

Bounded reconciliation takes exactly one stored owner/identity, authorizes only its deterministic uncommitted unreferenced quarantined path, removes that path, and records explicit 404 absence. Cleanup is verified only when no outstanding execution exists; otherwise absence remains a timestamped observation and cleanup_pending stays true. A retained execution can be settled later only from the original definitive transport outcome, never by a clock. New claims against quarantine/closed/revoked targets are refused. No committed receipt/legacy/referenced bytes are removed. The service-only reconciliation helper is reviewable source; no job or externally callable privileged route is deployed or scheduled by this slice.
