# TG-04: atomic one-use Telegram account binding

Status: local implementation and synthetic verification; no production application, bot deployment, or Telegram message sent.

The old `/start CODE` path selected a pending registration and later patched its identifier and `activo=true`. Concurrent consumers could reuse the read, and the write could reactivate a revoked registration. Both bot mirrors now call only `telegram_consume_binding_code` with the actual Telegram sender and username. Success and the menu require a typed confirmed result. An unavailable RPC or rejected result produces a concrete refusal without a direct-write fallback.

## Database candidate and authority boundary

[telegram-binding.sql](../../../src/sql/security-candidates/telegram-binding.sql) is a nonnumbered candidate. Its SECURITY DEFINER function has a fixed `pg_catalog` search path and fully qualified relation references. Only `service_role` receives EXECUTE; PUBLIC, anon, and authenticated are explicitly denied. It locks the matching pending registration, requires exactly one matching code, checks finite future expiry and explicit active status, and consumes the code while assigning the requested sender. The existing unique `telegram_id` constraint prevents taking over a sender already registered elsewhere.

For a linked registration, the function locks and requires its current `public.usuarios` profile to exist with `activo=true` and a role. It checks the profile again after the update. It verifies the durable row, exact sender, cleared code/expiry, and unchanged configured authority fields; suppressed writes or trigger changes raise an exception and roll back the transaction. The caller independently validates returned registration and linked-profile identity, active status, and the existing four application roles.

Captured metadata dated 2026-10-10 confirms that `telegram_usuarios.usuario_id` references **auth.users**, so that FK alone cannot establish an application profile. The code index is nonunique; ambiguous existing codes consume neither row. The candidate preserves this schema and introduces no new business policy or role mapping. The configured bot role/modules remain unchanged, and current application role is returned separately. Existing unlinked employee/contractor registrations retain their configured business lane. No profile mutation, module expansion, blanket reactivation, or default application role is introduced. Nullable modules become an empty local menu only when the RPC explicitly returns NULL.

Consumed-code replay refuses both the same and another sender. Ordinary `/start` without a code continues using the existing registration. This introduces no receipt table or new retention contract. Managers can revoke a pending code by clearing/rotating it or deactivating the registration; inactive or missing linked profiles also refuse admission.

## Verification and release gates

`python3 scripts/security/telegram-binding-postgres.py` passed 53 synthetic assertions and verified container/tmpfs cleanup on cached, digest-pinned PostgreSQL 17.6. It models the actual registration columns, auth.users FK, sender uniqueness, nonunique code index, and role enum, with explicitly synthetic supporting tables and timestamp trigger. It tests ordinary-role EXECUTE denial, invalid/expired codes, inactive/missing profiles, rotation, ambiguity, sender takeover, trigger suppression/mutation/deletion, expiry during a delayed write, exact one concurrent consumer, replay, and concurrent profile revocation. The revocation race observes a database lock barrier before starting the binding request. The container has no network, ports, or bind mounts and is removed in `finally`.

`src/__tests__/telegramBinding.test.ts` tests both mirrored helpers through the actual Supabase SDK HTTP serialization and extracts each real `/start` callback for execution. It verifies sender parameters, typed response refusal, linked-profile checks, configured role preservation, unlinked workers, explicit NULL modules, unavailable-RPC refusal, success/menu ordering, and the ordinary `/start` path. It sends no Telegram messages.

An approved release must apply the function under a trusted migration owner, verify its owner and exact ACL/body, confirm live constraints/columns/triggers and current role enum, then deploy both matching callers. Deploying callers before the function refuses new bindings. Test the actual RPC and webhook in an isolated owner-approved project, including concurrent consumption, code generation/rotation, inactive accounts, linked/unlinked registrations, and fresh workflow authorization. This local work does not deploy the candidate.

The service role remains a privileged boundary: compromised service credentials can bypass these application checks. The candidate verifies registration admission, not every later workflow write, so actions still require their fresh account guard. It does not define a mapping between bot and application roles. It does not certify real JWT/webhook verification, all live triggers, other privileged writers, or code-generation uniqueness under concurrent administrative writes. A concurrent code issuance path does not participate in the consume function's row locks; the existing nonunique index is not a global uniqueness protocol. These are bounded atomic-consumption tests, not a full Supabase Auth or Telegram certification.
