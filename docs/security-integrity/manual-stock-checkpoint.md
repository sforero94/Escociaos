# SI16 manual inventory movement — review checkpoint

Scope: the new manual-stock SQL candidate, isolated synthetic PostgreSQL harness, manualStockMovement utility and its SDK/React tests, plus NuevoMovimientoModal.tsx. No other writer changed. No production SQL, numbered migration, deployment, merge, credentials, notifications or spending occurred.

The original browser path inserted its ledger row and changed product stock in separate requests based on a previously read quantity. The caller now uses only the new atomic RPC. The server resolves auth.uid(), locks the existing active Administrador/Gerencia profile, uses the profile email for responsible attribution, locks the current product, and stores owner/key/exact-request evidence with full before/after product and movement snapshots. Final readbacks reject suppressed, altered or deleted rows, including a late receipt trigger changing the previously inserted ledger. There is no direct-write fallback.

Business types remain Entrada, Salida Otros and Ajuste. Entrada and Salida Otros require positive finite quantities that remain positive after decimal rounding. Ajuste preserves its original meaning: the supplied quantity is the desired nonnegative stock, including zero. Numeric normalization uses PostgreSQL numeric(12,2); client decimal rounding matches this contract and the preview uses the normalized quantity. Negative, missing or nonfinite current stock refuses mutation. Adjustments require the selected exact stock and nonnull updated_at revision to remain current, including the original fractional timestamp. Entries/exits apply deltas to the current locked quantity. Positive resulting stock reactivates the product, preserving the previous behavior.

An adjustment whose target already equals the current stock returns an explicit no-op receipt. It creates no fictitious zero ledger row and changes no product revision. The UI explicitly reports that no movement was created.

The durable client attempt belongs to the authenticated owner and product. Web Locks coordinate reservation/cleanup across tabs. Double submit in the same render is blocked. An uncertain response retains the key and original exact payload; a retry preserves the original observed stock/revision and automatically assigned date, including after midnight. Different business input refuses to replace uncertain evidence. Account changes prevent stale completion, success, draft clearing and delayed close callbacks.

A fresh owner-bound status RPC uses the same actor/key advisory lock. If the posting committed, it returns the exact original receipt. If no posting exists, it inserts and verifies a protected canceled marker before proving the operation unposted. Late concurrent operations with that key refuse to post. Only this fenced proof permits local pending state to clear; unavailable, malformed or ambiguous status keeps evidence. Failed stale corrections therefore require fresh product review without rebasing an uncertain original operation.

The receipt and canceled-marker records are prospective stock proof, separate from the memory receipt retention policy. A coordinated policy for stock proof retention, archival and eventual deletion remains a release gate; deleting retry fences without a replacement would permit historical key reuse. No historical actor or ledger proof is backfilled.
