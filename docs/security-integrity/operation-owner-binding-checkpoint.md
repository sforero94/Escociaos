## Narrow compatible fix partition for root review

1. **Mandatory server expected-owner guard (recommended correctness boundary).** Add a separate required expected-owner UUID argument to each affected public human RPC, populated from the durable attempt's original owner. After fresh trusted admission, require non-null `expected_owner = auth.uid()` before actor-scoped key lookup, posting, cancellation/fencing or receipt disclosure. Preserve actor provenance as trusted current Auth UID; never replace it with client owner input. Preserve existing payload exact-key validation, source CAS, signed amounts, receipts, worker lanes and actor-bound replay rules. Update post/reverse/status/resolve plus snapshot/proof selectors consistently; some status/resolve routes create cancellation proof rows and also need pre-write rejection. Legacy signatures/defaults must fail closed or be retired in the coordinated DB-before-caller release, rather than implicitly filling owner from the new session.
2. **Browser caller partition.** The five owned helper families can add only the expected-owner argument sourced from their saved attempt/current owner; do not create a new key or rebuild originals after mismatch. Keep all existing late receipt/owner/generation checks and pending-state preservation. Purchase/manual/catalog and closure/plan-delete can be separate exclusive implementation slices; their SQL/harness changes belong to the corresponding server-guard slice. The current proof assertions deliberately document bad behavior; convert the five cases to require zero wrong-owner commits once the guards are implemented.
3. **Captured-token alternative/defense.** Validate `getUser` and `getSession` owners, capture the exact access token, then send that immutable Bearer with this request through a request-scoped transport/client or configured HTTP RPC route. Do not mutate singleton global headers or use singleton `.rpc` after capture, because it reacquires the current token. CSV already demonstrates this fixed-token property, and activation checks/captures its token in its adapter. A switch before capture refuses; a switch after capture executes as A, the original operation actor, while existing final UI checks govern result handling. This is a request-binding fix, not a new account/creator permission. A server expected-owner guard remains the clearest coordinated fail-closed defense against any caller acquiring B unexpectedly.

The activation server route also creates a human client with the verified request's fixed Bearer token (`productos.tsx:85`); it must supply the verified actor if the catalog SQL public signature is tightened. CSV/activation header stability shown here is synthetic browser transport evidence; actual hosted Auth/RLS/Deno and SDK-version parity remain separate gates. No existing helper/SQL/source file was changed in this audit.
