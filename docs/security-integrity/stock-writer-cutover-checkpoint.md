## Actual ronda writers

`src/supabase/functions/server/telegram/ronda-helpers.ts:17` explicitly avoids direct product stock and inventory ledger DML. The stock writers are database RPCs. The tick (`ronda-inventario-tick.ts`) reads stock/price and ledger for reports; its writes to notifications/reports do not themselves mutate stock.

**Capture with backing evidence:** both `telegram/conversations/excepcionDavid.ts:592` mirrors call `fn_ronda_resolver_con_captura` through service role with actor_telegram_usuario_id, exception id, actual movement type/date/quantity and independently reconfirmed physical count. The freshly captured actual SECURITY INVOKER function calls `fn_ronda_validar_actor(...,'inventario_explicacion')`, locks the exception then product, requires exception=`explicada` plus David explanation, inserts ledger, changes stock, and marks `resuelta_con_captura`. It preserves Entrada, Salida por Aplicación and Salida Otros; salida ledger quantity is a **positive magnitude**, unlike the signed manual Salida Otros protocol. It does not change price; valuation uses the locked current price. Its state transition prevents a second successful capture but replay returns an error, not the original receipt. It coalesces null stock to zero, checks positive quantity and nonnegative resulting exit stock, but does not explicitly reject NaN/nonfinite inputs or normalize quantity before balance arithmetic. Half-cent rounding can make a stored magnitude disagree with the stored balance delta. INSERT RETURNING id and bare stock/exception UPDATEs lack suppression, exact persisted-row and late-trigger readbacks. Current physical-count reconfirmation is present in the actual captured function; it is not inferred solely from migration147.

**Approved adjustment:** both `telegram/bot.ts:1157,1164` mirrors call `fn_ronda_aplicar_ajuste` after approval, with actor_telegram_usuario_id, exception id, date and confirmar_cambio_teorico. Captured actual function tries any of inventario_ronda/inventario_explicacion/inventario_aprobacion, locks exception=`ajuste_aprobado`, then product. It calculates physical-minus-frozen-theoretical delta, applies that delta to current live stock, and refuses changed theoretical stock unless explicitly reconfirmed. It writes signed Ajuste ledger and marks `ajuste_aplicado`. It does not set stock to the physical count, change price or automatically reactivate product. It has a negative-result check, but no explicit finite/decimal checks, full stock/ledger/exception readbacks, owner/payload retry receipt, or exact observed-current version for the later force callback. State serialization prevents ordinary repeated posting but response-loss retries do not return the original outcome.

**Shared admission:** captured actual `fn_ronda_validar_actor` requires exactly one browser/Telegram actor. Browser auth.uid() must match declared usuario id, then it returns without checking application-profile active/role/module inside this helper. For a session without auth.uid(), it checks the declared telegram row's activo/module, without checking linked application user's current active role or locking either permission row. It does not itself prove that a no-auth call is from service_role. Actual invoker permissions/RLS/EXECUTE grants therefore remain part of the boundary. Root's strengthened bot callback checks do not replace database admission or serialize revocation with the stock write.

Minimal ronda cutover: preserve backed-capture versus approved-adjustment distinction, independent physical count, actual movement date, positive-magnitude versus signed type conventions, current-live delta rule, and Gerencia approval. Add trusted caller/sender-to-linked-account resolution, current active profile/module/role admission under permission-row locks, exact payload/action receipts bound to exception state, consistent numeric normalization, original version refusal for force confirmation, and final ledger/stock/exception readbacks. Repeated successful actions should return their original protected outcome without resetting the exception. A zero adjustment needs an explicit compatible terminal/no-op design; do not invent a zero ledger event or silently change exception FK/state semantics.

## Coordinated cutover requirements

1. Capture complete current writable function definitions/EXECUTE grants, target-table grants and policies, all triggers on product/ledger/purchase/application/daily/work/ronda tables, relevant FK deletion actions and scheduled jobs. Reconcile runtime/deployed mirrors. Use metadata only for this inventory; no domain-row inspection or RPC execution is needed to identify writers.
2. Choose one protected stock/price posting boundary, shared numeric convention and durable revision/proof contract. Preserve existing magnitude conventions where callers/reports depend on them; do not assume summing ledger cantidad with a single sign convention reconstructs stock. Lock products consistently in deterministic order and permission rows for current admission. Enforce invariant-bearing writes and final readbacks within the transaction.
3. Migrate product create/opening balances, CSV, price/catalog edits, activation, application closure and deletion, and both ronda stock RPCs before removing direct write access. Existing ordinary product/ledger UPDATE/INSERT/DELETE permissions can bypass the purchase/manual candidates. Removing them immediately breaks invoker closure/ronda browser execution and direct catalog create/edit; a compatible protected route must exist first. Service-role bypass also requires narrow entry points/protocol enforcement, not ordinary RLS alone.
4. Reserve an exact ordered release graph: compatible database boundary/receipts and upgraded server routes, then callers, then coordinated removal of bypass grants/legacy writable functions, with ordinary-role and service-role tests at the final boundary. No automatic numbered migration, deployment or live SQL is authorized by this checkpoint.
5. Preserve posted history during application/purchase cancellation and rollback. Keep requests, canceled-key fences, original/reversal movement proof and expense links; define stock-proof retention and archival separately from seven-day memory receipts. Never restore older snapshot stock over later farm work or delete post-release evidence to roll back code.
