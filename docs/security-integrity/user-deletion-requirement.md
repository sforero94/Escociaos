This is a requirement/design checkpoint, not a deployed-schema claim or authorized change to business permissions.

Observed current source: usuarios.tsx eliminarUsuario deletes public usuarios first and only then calls Auth admin.deleteUser. Auth failure can leave a live Auth identity without its profile. Required outcome: account revocation and Auth/profile reconciliation must not unintentionally discard farm conversations/memory/provenance or leave partial identities; retries and lost responses must retain a durable verified result. Existing owner requirement preserve farm records applies. Whether intentional permanent personal-history erasure is ever permitted remains a concrete business-policy acceptance gate; do not invent a blanket erasure/retention policy.

Technical preparation: inventory local and separately approved hosted FK/trigger/Storage/deletion graph; identify actual callers and current UI semantics; design durable deletion request with trusted fresh management actor, exact original target/profile, explicit domain-preservation preflight and immutable audit. Auth provider API and Postgres cannot form one transaction: use a replayable state machine with containment/reconciliation and no destructive profile-first step. Prepare supported soft-revocation first and only a separately reviewed deliberate permanent erasure path if authorized.
