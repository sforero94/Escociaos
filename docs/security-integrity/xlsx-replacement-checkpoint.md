## Recommendation

The smallest feature-preserving candidate is upstream **`exceljs@4.4.0`**, behind a narrow application spreadsheet adapter, with all SheetJS consumers migrated together before removing `xlsx`. It can be assessed through the approved npm registry rather than retrying the blocked patched SheetJS CDN. It is not a one-line dependency substitution: async workbook I/O, raw-date/error translation, first-sheet object mapping, browser download and Deno loading must be implemented and verified.

Do not claim ExcelJS is newly released or that a dependency substitution is already security-complete. Registry metadata identifies the genuine upstream `github.com/exceljs/exceljs` package, but its latest stable release is October 19, 2023; package metadata last changed December 20, 2024. Available npm metadata alone does not prove current upstream maintenance activity. It also does not certify its resolved transitive dependency graph. ExcelJS is a concrete compatibility candidate, subject to a narrow package/API/runtime/audit proof before adoption. If current active-release cadence is a strict acceptance criterion, this assessment has **not** found an equivalent maintained drop-in satisfying every existing contract.

More recently published upstream `read-excel-file` / `write-excel-file` packages were inspected as alternatives. They offer lean modern browser/universal entry points, but the reader's npm README explicitly states formula errors are silently ignored and interpreted as empty cells. Hato must preserve `#VALUE!` as a meaningful raw signal, so this pair cannot replace the current reader unchanged. The writer's published README establishes typed cells, widths, number formats and multiple sheets, but does not establish existing Print Titles and margins. Choosing these packages for a subset of exports would leave the vulnerable SheetJS readers in place and add a second compatibility layer; it is not the minimal complete remediation.

## Minimal adapter design and compatibility boundaries

Use the expected upstream ExcelJS `Workbook`, `addWorksheet`, `addRows`, `getCell`, column `width`, cell `numFmt`, worksheet `pageSetup.margins` / `pageSetup.printTitlesRow`, and asynchronous `workbook.xlsx.load`, `readFile`, `writeBuffer` APIs. These are the concrete API targets to verify against the package during implementation; ExcelJS's README was absent from the registry metadata returned in this assessment, and the package was not downloaded/installed or executed here.

Expose application operations rather than emulating SheetJS's entire mutable `utils` surface: an async ordered-sheet raw reader; an explicit header/fixed-key matrix-to-object mapper; a typed AOA workbook writer with names/widths/formats/print settings; and a Blob download helper. Preserve dynamic browser loading and existing try/catch diagnostics. Normalize CommonJS/default module shape explicitly instead of assuming browser, Node and Deno namespace imports agree. The current Hato workbook builder is synchronous because it receives the library; workbook construction can remain synchronous with an injected ExcelJS module, while serialization is awaited.

Raw-cell normalization is the highest-risk compatibility work:

- Direct strings/numbers/booleans stay typed. Null/missing cells stay null in Hato matrices; finance mappings still use empty strings. Do not automatically trim raw Hato strings, reinterpret text dates, stringify numeric amounts, convert errors to numeric codes, or turn `0` into an empty cell.
- Formula cells use their cached results, never execute formulas. Cached Excel errors must become their original error text, including `#VALUE!`; a missing cached result remains explicit empty/unsupported rather than a fabricated numeric result. Shared formulas, rich-text runs and hyperlink display text need deliberate mappings and synthetic fixtures; blindly calling `String(object)` is unacceptable.
- ExcelJS may expose date-formatted numbers as Date values, whereas current Hato inputs use `cellDates:false` numeric serials. Translate using UTC into the existing 1900-system serial contract, with fractional-date/rounding tests, or obtain original numeric values through a reviewed supported path. Never use process-local calendar getters for this translation. Existing Hato parsers intentionally use numeric serials only in known positional date columns and preserve malformed/multiple textual dates. Finance `parsearFechaFlexible` and monitoring's serial path must receive their existing compatible values.
- The existing Hato converter assumes a 1900 date system and intentionally does not handle serial-60's nonexistent 1900 leap day. A 1904 workbook needs explicit detection and either validated normalization or a clear refusal; silent behavior changes are forbidden. Historical/pre-1900 dates and sub-millisecond numerical-date precision are not established compatibility claims.
- Sparse cells, leading empty columns/rows, worksheet used-range origins, trailing blanks and ten free Hato template rows matter. ExcelJS iteration commonly omits empty cells unless requested; the adapter must retain the structure expected by the normalizer, not merely enumerate populated cells.

**Legacy binary `.xls` is a real supported-input gap.** Neither the ExcelJS XLSX path nor the recently maintained reader/writer pair provides an equivalent BIFF reader. Do not relabel `.xls` bytes as `.xlsx`, leave an unreachable `.xls` accept option, or retain vulnerable SheetJS as a fallback. A complete cutover needs an explicit coordinated contract for converting old files in Excel/LibreOffice to genuine `.xlsx`, or a separately reviewed maintained BIFF solution. This assessment found no such solution in the inspected packages. Existing emitted files are all `.xlsx`; no `.xls` fixture or observed production usage was examined.

Monitoring CSV needs a browser parser with quoted fields, delimiters, line breaks, headers and controlled type/date coercion compatible with current behavior. `csvProductImport.ts` is an inventory-domain parser with a specific schema, not an automatic generic monitoring drop-in. Arbitrary workbook/template style preservation is not a current feature: exports assemble new workbooks from data, and imports reduce them to raw values. Preserve the styles actually emitted (widths, numeric formats, margins, print titles), without promising macro support, formulas recalculation, or arbitrary third-party style round-tripping.

### Demonstrated adapter requirements

Two failures were reproduced before the corrected proof:

1. **Declared worksheet extent is lost by ExcelJS's reader.** Current SheetJS template XML declares `A1:M14`, including ten free rows, but ExcelJS's rowCount/dimensions from those source bytes ends at populated row 4. Simply iterating ExcelJS rows loses the existing phantom-row accounting. The proof overlays the declared dimension using genuine JSZip and Saxes, follows internal workbook-sheet relationships, and applies explicit synthetic bounds before constructing the raw grid. It does not alter cell values. The application adapter needs a separately reviewed bounded dimension strategy; copying this spike as a certified hostile-file parser is not authorized by these results. Declared dimensions, actual cells outside that range, malformed relationship targets and expansion budgets need explicit production handling. New ExcelJS-produced null rows also make its convenience dimensions getter incomplete; do not substitute that getter for the declared/source extent.
2. **SheetJS wch and ExcelJS column width are different units.** Directly assigning current wch values changes physical width, and a width of 9 is treated as ExcelJS's default and may disappear from metadata. The observed current SheetJS writer uses MDW=6: `Math.round((wch*6+5)/6*256)/256`. That conversion exactly matched existing serialized widths and new ExcelJS reload/XML values in the proof. This is a concrete current export contract, not a universal workbook/font conversion rule.

The 1904 fixtures demonstrate deliberate normalization into the existing **1900-system UTC serial** contract: raw XML serials differ by 1462 days while their loaded date/cached-date values normalize to the same July 22, 2026 noon serial. This improves the existing unsupported 1904 path only when the coordinated adapter explicitly owns that normalization. It does not establish serial-60, historical dates, all custom date formats or sub-millisecond numerical precision. No local-calendar conversion was used; both timezone executions passed.

### Pre-parser resource/admission enforcement

Input byte size is checked **before making the immutable copy**. Before `Workbook.xlsx.load`, the adapter validates central and local ZIP records, duplicate/canonical/non-traversing names, Unicode-path extra-field overrides, descriptors, CRC, bounded streaming actual inflation and declared/actual sizes; it refuses encryption, unsupported compression, multi-disk and ZIP64. Every XML/relationship part is bounded and parsed for well-formedness/DTD rejection. Actual worksheets require unambiguous internal workbook relationships with the supported OOXML namespace. Valid unrelated/external hyperlink metadata is preserved as display data without any network dereference.

Limits are compressed archive 20 MiB; entries 2,048; aggregate expanded bytes 64 MiB; individual XML/rels 16 MiB; sheets 64; maximum row coordinate 100,000/column 256; **whole-workbook** declared matrix/serialized-cell/shared-string/style counts 1,000,000; combined merged-cell extent 1,000,000 and 1,024 merge ranges. Declared dimensions, row/cell/column coordinates, malformed/duplicate/out-of-range shared strings/styles/shared formulas, mismatched counts and overlapping/out-of-dimension merges fail clearly before ExcelJS. A high-compression synthetic archive with deliberately false sizes proves actual inflation aborts in bounded chunks, not only trusting ZIP metadata. These are explicit resource/admission bounds, **not** fuzz certification or proof that every workbook within them fits a hosted 256 MiB process.

BIFF `.xls` names/signatures get explicit Excel/LibreOffice conversion instructions, with no legacy fallback. CSV gets an explicit separate-parser refusal. CSV caller integration remains outside this foundation.
