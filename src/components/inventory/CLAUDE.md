# Ronda de Inventario (`/inventario/rondas`, issue #175, `docs/plan_verificacion_inventario.md` + `docs/brief_tecnico_verificacion_inventario.md`)

Monthly physical-count control for the insumo catalog, built 2026-08-28 across migrations 124–130 and 6 implementation phases (0–6; **Fase 7, pattern-mining across ≥3 closed rounds, is explicitly deferred** until real usage exists). Replaces the never-finished `verificaciones_inventario`/`verificaciones_detalle` pair, which migration 124 froze read-only and rotuló as its one test row — `VerificacionesList.tsx` is now a legacy banner pointing here, and neither table nor its RPCs (`aplicar_ajustes_verificacion`, dropped by 128) is written to anymore.

**Three actors, three Telegram modules, one shared RLS pattern (044 variant).** Uriel (field counter, module `inventario_ronda`) opens/closes rondas, narrates findings by voice, never sees price. David (inventory custodian, module `inventario_explicacion`) explains every discrepancy and captures the real movement when there's backing evidence. Santiago (Gerencia, module `inventario_aprobacion`, `sensitive: true` in `telegramUsuarios.ts` since it exposes causa/delta) approves or rejects unbacked adjustments — the only human gate on money-moving without documentation. **The distinction is evidence, not size** (R-14): a backed movement (an application, a delivery, a real invoice) skips Santiago; an unbacked one (loss, theft, unclear cause) never does, no threshold. RLS on the 8 new tables: Group A (`rondas_inventario`, `rondas_inventario_alcance`, `rondas_transcritos`, `rondas_excepciones`) SELECT authenticated / write Admin+Gerencia / **no DELETE policy** (the one exception is `fn_ronda_deshacer_confirmacion`, which deletes via `service_role`, RLS-bypass); Group B (`rondas_reportes`, `rondas_avisos`) SELECT Gerencia-only, no write policy — only `service_role` writes; Group C (`inventario_causas_raiz`) SELECT authenticated, no write policy; Group D (`inventario_parametros`) SELECT authenticated / write Gerencia. `REVOKE ALL FROM anon` on all 8.

**The state machine is `rondas_excepciones.estado`, and CA-38 is enforced by two separate columns, not a flag.** `explicacion_citada` (what Uriel's voice note quoted David as saying) and `explicacion_david` (what David actually confirmed/corrected/said, with `explicacion_david_en`/`_accion`) are structurally distinct — a `CHECK` (`excepcion_avanza_solo_con_david`) makes any state past `explicacion_precargada` unwritable without `explicacion_david_en IS NOT NULL`. The nine states: `reportada` → (`explicacion_precargada` if Uriel's note quoted David) → `explicada` → either `resuelta_con_captura` (vía a, David captures the real movement, `fn_ronda_resolver_con_captura`, never logged as `'Ajuste'`) or `ajuste_propuesto` → `ajuste_aprobado`/`ajuste_desestimado` (Santiago, `fn_ronda_decidir_ajuste`, `decision_causa` always required — CA-11) → `ajuste_aplicado` (delta over the LIVE balance, never a fixation — `fn_ronda_aplicar_ajuste` warns and refuses to apply silently if the live theoric changed since the count, CA-2).

> **KNOWN GAP, verified live, not fixed as of 2026-08-28 — `cerrada_sin_ajuste` is unreachable.** It is a real ENUM value and one of the three terminal outcomes CA-10 requires distinguishable, but **no RPC in migration 126 or its correction 130 ever writes it**. When David says "no backing needed" in `excepcionDavid.ts`, the exception simply stays `'explicada'` forever unless someone calls `/proponer` — and `fn_ronda_proponer_ajuste` always routes through `ajuste_propuesto`, even for causa `error_de_conteo` (`via='ninguna'` in `inventario_causas_raiz`, which per the causa→vía table is supposed to mean "closes with no inventory movement, no Santiago"). There is no RPC path from `explicada` straight to `cerrada_sin_ajuste`. Needs a scoped fix (most likely: `fn_ronda_proponer_ajuste` special-cases a causa whose `via='ninguna'` and closes directly, or a new small RPC) plus a UI affordance in `excepcionDavid.ts`/`bot.ts` — flagged to the owner, not fixed blind.

> **KNOWN GAP, verified live, not fixed as of 2026-08-28 — R-16/CA-14 (free-text observation for an uncatalogued product) has no path.** `interpretarNota.ts`'s prompt explicitly instructs the model to **never** route a mentioned product to `observaciones_libres` — it always becomes a `hallazgo`, and if it doesn't match the frozen scope it becomes `no_identificado`. `fn_ronda_confirmar_hallazgos` then **rejects the entire transcript's confirmation** (CA-32) if even one hallazgo has no resolved `producto_id` — there is no per-item drop/degrade-to-free-observation path, so a single genuinely-uncatalogued mention blocks confirming every *other* legitimate finding in the same voice note until Uriel corrects it into something that matches the catalog (which, by definition, it can't) or exhausts `MAX_INTENTOS_PREVIEW` and lands `sin_confirmar`. `rondas_inventario.observaciones_libres` (a header column from migration 125) exists but nothing writes it. Needs a prompt/schema change in `interpretarNota.ts` distinguishing "can't match the catalog, still a real hallazgo" (should stay blocking, CA-32's real intent) from "not a catalog item at all" (should degrade to free observation, R-16), plus per-item confirmability in `fn_ronda_confirmar_hallazgos`/`resolverHallazgos.ts`.

**Every RPC takes `payload jsonb`, is `SECURITY INVOKER`, and the actor is ALWAYS explicit** (`actor_usuario_id`/`actor_telegram_usuario_id`, never derived from `auth.uid()`/`auth.jwt()`) — the reason is D-T4: `service_role` (how the Telegram bot calls every RPC) has `rolbypassrls`, so RLS isn't even evaluated, but any expression deriving the actor from the session silently resolves to NULL. `fn_ronda_validar_actor(p_usuario, p_telegram, p_modulo)` is the single point deciding whether the declared actor is valid — browser sessions can only claim themselves, `service_role` calls must resolve to an active `telegram_usuarios` row with `p_modulo` in `modulos_permitidos`. `fn_ronda_decidir_ajuste`'s Gerencia gate is the one exception that does **not** use `es_usuario_gerencia()` (that SECURITY DEFINER helper reads `auth.uid()`, which is NULL under `service_role` and would always return false) — it walks `telegram_usuarios.usuario_id → usuarios.rol = 'Gerencia'` directly. `fn_ronda_proponer_ajuste` authorizes `inventario_ronda` OR `inventario_explicacion` (David or Uriel — corrected 2026-08-28 from the original migration 126, which only authorized David; Santiago's literal words in the interview were "el ajuste lo puede proponer David o Uriel"). `fn_ronda_aplicar_ajuste` authorizes any of the three modules (B-7: applying an already-approved adjustment is mechanical — what CA-9 protects is the `estado='ajuste_aprobado'` guard, not who executes). **Migration 130 (2026-08-28, applied same day as 126) is a `CREATE OR REPLACE` correction, not a new migration in the plan** — `fn_ronda_proponer_ajuste` was the only one of the ten RPCs missing a state re-check (it only required `explicacion_david_en IS NOT NULL`, a condition that stays true forever), so a replayed/stale Telegram `callback_data` on an already-decided-or-applied exception could reset it back to `ajuste_propuesto` and open a path to a second application of the same adjustment. Never modify 126 or 130 directly — a further fix is another `CREATE OR REPLACE` migration.

**The voice pipeline is two separate model calls, never one** (D-T6): `transcribirNotaVoz` (STT, `openai/whisper-large-v3-turbo` by default, override via `RONDA_STT_MODELO`) produces the raw layer saved verbatim to `rondas_transcritos.transcrito` (CA-36 — never rewritten, not even by a later correction, which re-interprets the ORIGINAL transcript plus the accumulated correction history, never edits it); `interpretarTranscrito` (`google/gemini-3-flash-preview` by default, override `RONDA_INTERPRETE_MODELO`, `response_format: json_schema`, `temperature: 0`) interprets that TEXT into structured hallazgos. If they were merged into one call, a mishearing ("Silicalmag" → "Silicio") and a genuine misinterpretation would be indistinguishable. Product resolution is **exact normalized match only, never edit distance** (D-T7) — an unmatched product becomes `no_identificado` and a human picks it, never auto-mapped to the closest name. The physical quantity Uriel narrates is always shown against the SYSTEM's theoretical (frozen at ronda-open, R-5), never the number Uriel said (R-19) — a derived físico (Uriel says "missing 3" over a theoretical of 8) is labelled `derivado`, never `dictado`. On any interpreter ambiguity or low confidence, the default is always the MORE-controlled path (`aprobacion_gerencia`, R-18) — the system's bias toward asking Santiago is asymmetric on purpose. **This session could not exercise the STT call against a real Telegram voice note** — `OPENROUTER_API_KEY` is a write-only edge function secret no session in this implementation chain could read, and Telegram sends Ogg/**Opus**, which OpenRouter's docs only confirm as "Ogg Vorbis" — if the pair fails with a specific format error once deployed, the documented fallback (§5.7 of the technical brief: a structured `/hallazgo` command) is NOT built yet, deliberately, until a real failure is observed.

**Telegram surface** (`src/supabase/functions/server/telegram/bot.ts`, `ronda-helpers.ts`, `conversations/{cierreRonda,excepcionDavid}.ts`, `ronda-voz-pipeline.ts`, mirrored into both edge-function trees per `docs/inventario/regenerar-copias-ronda-inventario.py`): `/ronda` (status/open), `/existencias <texto>` (qty+unit only, R-15, never price), `/cerrarronda` (conversation, A-5), voice notes → preview loop (`[Confirmar]`/free-text correction/`[Descartar]`/`[Deshacer]` — the last one is `fn_ronda_deshacer_confirmacion`, same button-with-id-in-callback_data pattern as `hato_ev_undo`, only valid while the ronda is still `en_curso` and nobody's excepciones from that transcript have been touched by David yet), `/explicar` (David's pending list → `excepcionDavid` conversation per exception), `/proponer` (David or Uriel, causa picker, two-step callback `rpa:<id>:c<n>` → `:ok`, never a conversation), `/aprobar` (Santiago, same two-step shape, `rda:<id>:(A|D):c<n>` → `:ok`, auto-applies immediately on approval). **The ronda itself is never a Grammy `conversation`** (D-T9) — it lives for days, a `conversation` would swallow every other command (including `/existencias`, which Uriel needs *while* counting) while active, and CA-37 requires an unconfirmed draft to survive a redeploy. Only `cierreRonda` and `excepcionDavid` are real conversations (short, single-purpose, explicitly reject a voice note mid-flow). Causa raíz is encoded as a 1–7 index (`causaPorIndice`/`indiceDeCausa`) in `callback_data`, never the literal clave — the longest key plus a UUID plus a decision letter exceeds Telegram's 64-byte `callback_data` limit.

**The tick** (`POST /make-server-1ccce916/inventario/ronda/tick`, `ronda-inventario-tick.ts`, pg_cron `ronda-inventario-tick` at `'0 12 * * *'` = 07:00 Bogotá, migration 127): four idempotent jobs keyed in `rondas_avisos` — reminder (day 1 or a postponed date, A-1/A-4; postpone is 3 quick buttons, mañana/+3 días/+1 semana, since A-4 doesn't specify mechanics), the day-15 message to Santiago (two independent blocks — month-skipped and exceptions-open->30-days, neither hangs off the other, §8.1 is explicit about that), and the closing report (C-1, assembled by `construirReporteCierre`/`renderReporteCierreTelegram` in `reporteCierre.ts` — pure, built in Fase 1 before the tick existed — then persisted once via `fn_ronda_emitir_reporte`, which never recomputes, R-10). **Report emission uses two DIFFERENT idempotency mechanisms on purpose**: `rondas_reportes`'s PK freezes the *content* forever; a separate `rondas_avisos` key (`reporte_cierre:<ronda_id>`) confirms the *send*, and — unlike the other three jobs, which claim their key BEFORE sending — this one claims AFTER a successful send, so a Telegram failure retries tomorrow with the same frozen text instead of losing the alert. Auth is the same double-door as `hato-alertas-tick.ts`/`acciones-tick.ts`: header `x-inventario-tick-secret` against `INVENTARIO_TICK_SECRET` (**unset → 503, never runs open** — same contract as the other three tick secrets), or JWT+Gerencia for a manual run. **Movements shown in the closing report as "occurred with the ronda open" (R-9) use TWO different date fields on purpose**: a movement linked to one of this ronda's own exceptions (by `captura_movimiento_id`/`aplicacion_movimiento_id`) is included regardless of its `fecha_movimiento` — David is explicitly asked for the movement's *real* date (CA-8, never "today" by default), so a capture entered today can legitimately carry a `fecha_movimiento` from weeks ago, and filtering by that field alone would silently drop it from the report despite being unambiguously tied by FK. Unlinked movements (the `ajuste_puntual`/`entrada_fuera_de_alcance` buckets) are windowed by `created_at` instead — the question R-9 is actually answering for that bucket is "did something get written to the system while the ronda was open, without going through Santiago," which `created_at` answers and a human-entered `fecha_movimiento` does not. `INVENTARIO_TICK_SECRET` provisioned in Vault (`inventario_tick_secret`) and as an edge function secret 2026-08-28.

`inventario_parametros.valoracion_publicable` gates every valuation figure across this whole module (closing report's total value + month-over-month delta, and would gate the day-15/reminder messages if they ever grew one) — seeded `false` by migration 125, **still `false` in production as of 2026-08-28**. Flipping it is a Gerencia sign-off, not a code change (the phase table's own acceptance criterion for the price-catalog sanitization work was literally "`valoracion_publicable = true` firmado por Gerencia") — nothing in this module should flip it programmatically.
